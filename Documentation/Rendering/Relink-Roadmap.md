## 1. 本轮结果与开始条件

本轮已分析异常捕获的 56 个代表事件，随后修复捕获并细查正常帧的 34 个事件，保存资源清单、Shader 反汇编及选取常量。原始 `relink_frame18802.rdc` 中建筑、地面、人物缺失，保留用于诊断；后续以 `standard_d3d11_frame10803.rdc` 为主要参考。

| 启动条件 | 现场画面 | 捕获 / 回放 | 结果 |
| --- | --- | --- | --- |
| 原始 RenderDoc 注入 | 主体几何缺失 | 内置缩略图和离线回放同样缺失 | 异常样本，保留作兼容性诊断 |
| 无注入启动，已载入城镇 | 地面、石阶、建筑、树木、NPC 和角色完整 | 此组不注入捕获工具 | 已通过现场基线核对 |
| RenderDoc + `NV.BlockNVAPI=true` + CaptureAllCmdLists | 完整城镇与人物；日志确认设置已加载 | 三张新 RDC 均成功回放；主样本 GBuffer 和阴影含主体几何 | 当前兼容性修复及重复捕获通过 |

无注入对照已证明问题出现在注入条件下。新配置下主体几何恢复，原 MultiDraw 拒绝日志不再出现，tiled resources 警告仍存在。`CaptureAllCmdLists` 与 NVAPI 开关同时变化，这次证明的是该组合可用；单独的接口警告还不能确定唯一原因。

阶段 0 的当前捕获兼容性、主要中间目标和重复回放验收已通过。尚未完成的是连续帧历史分析、逐像素等价，以及分离两个开关影响的单变量实验；这些是后续证据工作，不阻塞 GBuffer 数据契约的工程验证。

## 2. 阶段 0：取得可信的完整帧

**本轮已满足当前场景的基础捕获条件。** 以下流程用于新的地图、设置、驱动或捕获工具版本；跨帧和像素级验证仍需继续。

1. 在同一城镇和接近镜头位置核对无注入画面，记录游戏版本、GPU、驱动、分辨率与画质。
2. 用 `Tools/Rendering/launch_relink_capture.ps1 -Mode StandardD3D11` 进行可回滚实验。确认捕获进程日志确实加载 NV 开关，并在游戏现场确认主几何完整。
3. 若现场正常，捕获一帧；核对现场、内置缩略图、交换链离线回放。检查对应深度、GBuffer 和阴影层里也有地面、建筑与人物，避免只检查最终 UI。
4. 有效帧重新建立事件映射；旧帧事件编号不能直接套用。对相同 Shader 的哈希、绑定和常量复核，记录新增/缺失的绘制。
5. 保存相邻或可重复捕获，观察曝光、时域历史、速度符号和遮挡变化。单帧无法验证历史重置与跨帧稳定性。

交付：有效 RDC、SHA-256、诊断日志、缩略图和回放图、带有效性说明的清单，以及正常帧事件表。

验收：三处画面都有主要几何；离线回放没有关键绘制丢失；中间目标覆盖完整场景；同一条件至少一次重复成功。这里只要求结构和主要内容一致，不用不同时间的动画像素差证明错误。

若标准回退失败：保留失败日志和配置结果；在工具源码确认 MultiDraw 兼容性及 DX11.2 接口路径。后续可评估支持该接口的捕获工具，或为 RenderDoc 添加正规的记录/回放封装。不能把放行 unsupported vendor extensions 当成有效捕获；也不直接修改游戏二进制。此阶段结束前，旧帧仅用于资源和算法研究。

| 5. 天空与空间效果 | 天空立方体、区域/高度雾、植被和专用前向效果 | 场景组件和叶片材质变体 | 天空、雾、透明与调色时序一致；叶片正反面及运动正常 |
| 6. 曝光与调色 | 亮度历史、近远两套 3D LUT、分类调色、多尺度 Bloom、实测电影曲线 | 每级中间目标及参数预设 | 曲线数值可复查；曝光收敛；Bloom 与 sRGB 时序正确 |

## 4. 阶段 1 的具体工作包

这是捕获问题解决后优先执行的工程改动，范围可独立评审。

### 4.1 GBuffer 契约

- RT0：sRGB 底色 + 分类标志；明确 RTV/SRV 与 Unity RenderTexture 的读写空间。
- RT1：金属度、粗糙度、间接光衰减及保留通道；尚未解码的 A 通道不任意赋予原游戏含义。
- RT2：视空间法线编码及分类/保留通道。
- RT3：RG16F 屏幕 UV 速度；明确当前位置减前帧位置，投影 jitter 是否包括在内及历史采样的符号。
- 深度/Stencil：在 Unity D3D11 上确认可采样视图与 Stencil 读取办法；不可访问时采用显式类别目标，并记录与原布局的工程差异。

先使用普通底色、BC5 法线及 mask 输入实现清晰的材质接口。缓存页表、虚拟纹理反馈和流式调度独立列为后期工作，不让它阻塞延迟照明验证。

### 4.2 SRP 改动位置

| 现有位置 | 改动方向 |
| --- | --- |
| `Assets/RelinkStyle/Runtime/RelinkRenderPipeline.cs` | 拆分资源准备、阴影、GBuffer、照明、前向、后处理和输出阶段；增加采样标记及明确资源寿命 |
| `RelinkRenderPipelineAsset.cs` | 保留原型模式，增加延迟路径与模块调试开关；配置与美术参数分开 |
| `Shaders/RelinkEnvironment.shader` / `.cginc` | 共用材质读取与顶点变形；新增 GBuffer / Motion Pass，保证深度与颜色使用相同叶片裁剪 |
| 新增光照 / 阴影 / IBL Shader | 按有效帧的输入输出契约实现；每个阶段都有单独可预览目标 |
| `Shaders/RelinkComposite.shader` | 渐进替换当前曲线与调色；跨帧资源由管线管理，单帧 Composite 不承担历史状态 |
| `Editor/RelinkSceneTools.cs` / 验证工具 | 生成固定镜头的材质球、阶梯、墙角、细叶片、探针交界和移动物体场景 |

资源数量和精度先服务于可核对性，再按测量合并 Pass。采用 SRP 的上下文和 CommandBuffer 完成调度；是否引入 RenderGraph 作为后续工程选择，不更换为 URP。

### 4.3 验证场景

使用固定曝光和固定镜头，包含粗糙度/金属度材质阵列、已知法线方向、远近阶梯、不同接触距离的遮挡、双色 IBL 交界、静止与移动物体及叶片。保存底色、mask、法线、速度、线性深度、分类、直接光、阴影和间接光视图。

验证聚焦数据契约、坐标与历史生命周期，不为纯菜单文字或可逆低影响改动增加镜像实现的测试。现有 `SRP-Validation.txt` 可作为渲染运行基础，不作为正常游戏外观验收。

## 6. 捕获与分析操作

启动实验前正常保存并退出游戏。启动工具拒绝关闭现有进程，不写游戏文件；`StandardD3D11` 在启动时短暂改变 RenderDoc 全局配置，并在 `finally` 中恢复。

```powershell
& 'Tools/Rendering/launch_relink_capture.ps1' -Mode Baseline
# 核对场景，正常退出游戏，然后执行第二组。
& 'Tools/Rendering/launch_relink_capture.ps1' -Mode StandardD3D11
# 使用启动工具返回的 TargetPort；不要把成功返回的目标 ID 误判成失败码。
$env:RELINK_TARGET = '38920'
$env:RELINK_CAPTURE_OUTPUT = Join-Path (Get-Location) 'Captures/Relink/StandardD3D11'
$env:RELINK_CAPTURE_MODE = 'capture'
& 'Temp/RelinkTools/RenderDoc/RenderDoc_1.46_64/qrenderdoc.exe' --python (Join-Path (Get-Location) 'Tools/Rendering/capture_relink.py')
```

捕获必须在已验证的场景中触发，不能在标题画面触发后算作完整场景成功。退出捕获进程前保存 RenderDoc 诊断日志；部分日志会随进程关闭消失。

离线使用 `inspect_relink_capture.py` 先做 inventory，再按新事件编号选取细查，不复用旧编号。每次新样本在单独目录输出，记录失败及有效性，不覆盖此前证据。检查输出 JSON 中的完成状态；GUI 启动程序返回不一定意味着脚本结果已经写完。捕获脚本已过滤重连时收到的旧捕获通知，以时间戳和 capture ID 确认本次请求。

本轮 RenderDoc 位于 Unity `Temp` 中；若该目录被 Unity 清理，启动脚本可通过 `-RenderDocDirectory` 指向保留的 RenderDoc 1.46 安装。分析示例中的 `qrenderdoc.exe` 路径也应相应调整。

## 7. 完成定义

项目的完成不是“有一张相似的截图”。应交付可启用的独立 SRP、可信的逐阶段证据、可复现的场景与参数、已解释的差异以及实际性能结果。场景优先完成后，再对角色面部、皮肤、头发、描边和战斗特效做独立专项逆向；不把角色 Shader 假设套用到整个场景。
